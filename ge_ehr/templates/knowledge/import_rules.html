How rule revisions work

  1. Validate. Every rule is checked strictly; an error names the rule and the field. A stored version can never change: publish a correction as a new version.
  2. Store. Unseen versions are added; the highest version of each rule becomes current.
  3. Re-run. Each revised rule is re-run for the carriers of its old and new genes. Patients are notified only when the outcome changes — e.g. D4 v2 adds ABCC8, so ABCC8 carriers on insulin are newly alerted. A withdrawn alert raises a review notice.
Document format 
{
  "rule_set": "GE-EHR monogenic diabetes rules",
  "label": "v2 (2026)",
  "rules": [{
    "code": "D2", "version": 1, "kind": "treatment",
    "title": "HNF1A diabetes on insulin or metformin",
    "genetic": {"genes": ["HNF1A"], "classes": ["P", "LP"],
                "mechanism": null},
    "clinical": {"any_of_drug_classes": ["insulin", "metformin"],
                 "none_of_drug_classes": ["sulfonylurea"]},
    "severity": "high",
    "recommendation": "Consider low-dose sulfonylurea …",
    "source": "Kang et al. 2021; Naylor et al. 2024",
    "change_note": "Initial version"
  }]
}

clinical: null means no therapy condition. Allowed keys: any_of_drug_classes, none_of_drug_classes, max_age_at_diagnosis_months.
